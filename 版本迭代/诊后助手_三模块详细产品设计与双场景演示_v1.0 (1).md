# 诊后助手：三模块详细产品设计与双场景流程演示

**版本**：设计提案 v1.0｜**日期**：2026-11-03｜**用途**：团队讨论、两位医学生审核、WorkBuddy 开发输入、黑客松演示基准。

> **核心结论**：不另起炉灶。保留现有「安排／记录／复诊」三个导航、四类行动卡、原话与 AI 整理对照、三段式复诊卡、纸感备忘录视觉；补足「复诊周期＋统一数据＋来源核对＋状态机＋摘要版本」五项底层机制，使三个模块真正互通。术后出院为主演示，高血压复诊仅验证机制可复用。以下标注【拟议】的部分是基于材料的产品推断，不能写成已完成临床需求验证。

## 0. 一页决策摘要

**服务对象**：有明确既有诊疗安排、处于离开医院至下一次复诊之间的患者；重点研究术后出院、涉及多项安排且可能由家属协助的情境。高血压等慢病复诊是扩展验证，不是第二套软件。

**用户收益**：离开医院以后清楚“已有安排是什么—我记录了什么—还有什么要问”，复诊时拿出一份由本人核对、可追溯到原始记录的沟通卡。

**不做什么**：不生成新的医嘱、不判断症状危险程度、不推断治疗效果、不调整剂量或指导漏服补服、不向未对接的医生发送消息、不把无记录等同于未执行、不自动续用旧周期的医嘱。

**三个模块**：

- A「安排」——既有医嘱导入、提取、逐项核对、四类行动卡、按需提醒与操作记录；
- B「记录」——患者的事实、主观变化、数值监测、疑问及可验证渠道；AI 只负责受限的文字整理；
- C「复诊」——汇集 A/B 的事实与问题、逐条核对、生成三段式复诊沟通卡、诊室模式、周期归档。

**一条主线**：建立周期 → 导入来源 → 核对安排 → 执行与记录 → 复诊准备 → 人工核对 → 诊室使用 → 归档／开新周期。

**比赛成功标准**：真实地完成上述数据流；高血压场景无需开发新的一套模块即可运行；能演示至少一次错误/未知信息被阻止变成确定结论、一次私人记录不外发、一次修改后摘要核对状态失效。

## 1. 依据、证据等级与产品假设

### 1.1 来自团队已收集材料

| 材料 | 目前能够支持什么 | 不支持什么 |
|---|---|---|
| 《医生.docx》访谈：儿科、心内科内容 | 医嘱可归纳为用药、复查、康复禁忌、就医提示；复诊时医生关心症状变化及检查资料 | 不能直接证明骨科全部医生工作流、接诊者必然有时间看复诊卡 |
| 《患者疑问.doc》术后问题清单 | 与用药、恢复预期、伤口护理、康复、风险、流程有关的疑问值得考虑 | 是设计问题集，不是患病人群需求比例调查，更不是已验证的问答效果 |

| 六屏交互原型与纸感视觉方案 | 确认已有导航、文案风格、组件和状态表达的设计基础 | 不能视为所有后台记录、提醒、AI 提取和跨页同步已实现 |

### 1.3 仍待验证的关键假设

H1 患者真正的障碍是否是“安排分散、时间不清、复诊时回忆困难”；H2 家属是否需要承担部分录入且必须区分记录者身份；H3 患者会不会使用语音比打字更轻松；H4 医生/护士是否认可三段式摘要的阅读顺序与信息粒度；H5 记录频率低时，用户仍认为按需记录值得使用。

原则：设计可以先按假设执行，但作品文档中不得把 H1–H5 写成已验证结果。

## 2. 用户角色、场景和信息架构

**患者**：诊疗安排主体；可查看、记录、核对、决定哪些信息用于沟通。

**家属／照护者**：协助导入和记录；本次比赛只做同设备“代记标识”，不做多账号权限同步；代记不等于患者本人核对。

**医生**：复诊卡的潜在接收者，不必登录产品；展示是患者自主出示或本地导出。没有医院接口时，不显示“医生已收到／已审核”。

**管理员／产品团队**：制作合成演示数据，验证流程。不得将比赛版接入真实患者敏感资料。

### 2.1 页面结构（沿用现有风格，补足逻辑）

| 导航 | 页面代号 | 名称 | 核心动作 | 现有基础／本次变化 |
|---|---|---|---|---|
| 安排 | S01 | 当前安排 | 查看下一件事／提醒／待问摘要 | 现有首页保留；改为读取当前周期真实状态 |
| 安排 | S02 | 导入与核对安排 | 输入原文、逐条编辑、核对来源 | 现有核对页保留；扩展为多张可选行动卡 |
| 安排 | S03 | 行动卡详情 | 查看原文、记录执行、提醒开关 | 原框架已规划；补齐真正的数据写入 |
| 记录 | S04 | 记一件事 | 文字／语音、数值监测、保存去向 | 现有记录页保留；接入统一记录表 |
| 记录 | S05 | 疑问与 AI 整理 | 原话对照、整理疑问、渠道入口 | 现有整理页保留；对选中记录真实生效 |
| 记录 | S06 | 记录及待问清单 | 列表筛选、私人标识、问题状态 | 现有列表可承接；不一定需要独立底部入口 |
| 复诊 | S07 | 摘要选择与核对 | 勾选数据、生成草稿、核对来源 | 现有核对摘要保留；由真实数据动态构建 |
| 复诊 | S08 | 沟通卡与诊室模式 | 大字展示、逐条“已问过”、归档 | 现有沟通卡保留；加诊室模式及归档保护 |

底部导航固定为“安排／记录／复诊”，无需增加第 4 个入口。“历史周期”从设置或复诊页的轻量入口进入。

## 3. 共用底座：真正打通三个模块的机制

### 3.1 核心数据对象

| 对象 | 必需字段（示意） | 谁创建／谁使用 |
|---|---|---|
| `Cycle` 复诊周期 | `id, scenario, startAt, plannedReviewAt?, status` | 初始创建，A/B/C 全部绑定该周期 |
| `SourceDoc` 原始资料 | `id, cycleId, text, mediaRef?, sourceType, capturedBy, capturedAt` | A 导入；用于所有来源核对 |
| `Instruction` 已有安排 | `id, cycleId, category, sourceDocId?, sourceQuote?, fields, dateBasis?, verifyStatus, verifiedBy?` | A 提取／手填；A 展示，C 摘录 |
| `ActionLog` 操作记录 | `id, cycleId, instructionId, actionType, loggedAt, recordedBy` | A 产生；C 汇总事实 |
| `Observation` 变化／监测 | `id, cycleId, type, textOrValue, unit?, occurredAt, createdAt, recordedBy, privacy` | B 产生；C 选择纳入 |
| `Question` 待问问题 | `id, cycleId, sourceRecordIds[], originalText, editedText?, status, privacy` | A 的待确认或 B 的疑问产生；C 展示 |
| `Summary` 复诊卡版本 | `id, cycleId, selectedIds[], linesWithSources[], status, revision, verifiedBy?, verifiedAt?` | C 生成／核对／导出 |
| `Channel` 联系渠道 | `name, phone?, infoSource?, checkedAt?, region, verified` | 团队预置已核实公开信息或用户明确保存，不用 AI 猜 |

**最低实现**：一个浏览器本地数据库（如 IndexedDB）或明确的本地存储模型就能承载比赛闭环；按周期 ID 串联，不需要医院后端。涉及音频可用 IndexedDB 存储，避免依赖 `localStorage` 保存大文件。交付必须写清刷新后的持久化边界和是否只在当前设备有效。

### 3.2 五组状态不允许混淆

| 维度 | 允许状态 | 不能推出什么 |
|---|---|---|
| 医嘱内容核对 | `待核对 / 已由某人核对 / 待确认` | 核对过 ≠ 医学专业审核 |
| 行为记录 | `未记录 / 已记录执行 / 用户主动标记未完成` | 未记录 ≠ 没有执行；已记录 ≠ 医学上依从良好 |
| 提醒 | `未启用 / 用户启用 / 模拟提醒` | 模拟触发 ≠ 真正系统推送 |
| 问题 | `待问 / 已问过 / 暂不展示` | 已问过 ≠ 已得到医生答复 |
| 沟通卡 | `草稿 / 本人或家属核对版 / 有内容更新待复核 / 已归档` | 用户核对 ≠ 医生确认／病情稳定 |

每个改变都必须体现：**是谁、在什么时间、针对什么记录做了什么**。不要用一个通用 `done=true` 处理所有状态。

### 3.3 五条跨模块数据通路

| 触发 | 写入什么 | 影响哪里 | 设计目的 |
|---|---|---|---|
| A：核对行动卡 | `Instruction` 的核对人、状态 | S01 下一件事、S03 明细、C 已有安排 | 避免未核对医嘱直接当作有效提醒依据 |
| A：记录某次执行 | `ActionLog` | S01 事实计数、C 处理记录 | 不需要复诊前重复回忆和填写 |
| A：内容缺失时“加入待问” | `Question(source=Instruction)` | B 待问列表、C 待问问题 | A 与 B 的第一个直接打通点 |
| B：记录一件事／监测数据 | `Observation`；选择待问时另建 `Question` | B 时间线、C 候选素材 | B 与 C 自动共享；保留原始记录 |
| C：生成／核对／归档 | `Summary` 的来源快照、版本及周期状态 | S08 展示、S01 周期入口 | 数据一致、可追溯，且不会将旧医嘱自动带到新周期 |

**重要规则**：A、B 可以平行使用；C 只在需要准备复诊时汇集。不能要求患者按“先做 A 再做 B”的严格顺序操作。

### 3.4 数据一致性和摘要失效规则

1. C 构建草稿时只从本周期“被选中的记录”读取事实；默认不选私密记录。
2. 结构化数值、次数、日期由程序按事实计算并列示；AI 不自行猜测测量频率、恢复情况或诊断。
3. 对摘要每一行保存 `sourceIds` 和原始文段，支持“查看来源／撤回此条”。
4. 用户编辑摘要后，状态回到“待重新核对”；被引用的来源记录发生变化时，旧的“已核对”标识失效。
5. 新增了未选择的记录时，显示“有新记录未纳入”，允许用户保持当前版本或重新生成，不偷偷修改原摘要。
6. 分享／打印展示只从用户核对版产生，且只包含明示选中的内容；无数据写“本周期未记录”，绝不能写“无异常”。
7. 周期归档会停掉本轮软件提醒并将历史记录只读化；新一轮必须重新创建或重新核对安排，绝不自动续药。

## 4. 模块 A：诊疗安排延续（安排）

### 4.1 用户任务与角色

用户在诊室或出院后手持一张难以快速执行的医嘱说明，需要在最少操作内搞清楚：下一步是什么、什么时候、还有哪一项没弄明白。家属允许帮助录入，但每一项应标记录入者和核对者。

### 4.2 功能定义与交互

**A1 建立周期（P0）**：从“创建新周期”开始，选择“术后出院／门诊复诊／其他”、填写就诊或出院日期；复诊日期可以为空。系统不得要求选择确切疾病或填写过多医疗资料才允许进入。输出 `Cycle.status=active`。

**A2 医嘱导入与信息提取（P0）**：支持粘贴文字或手动输入；图片 OCR／拍照可作为 P1，但缺失时必须能完成人工输入。若有 AI，要求仅提取**已有原文中的字段**：类别、原句、药品文字、时间、地点、注意事项、就医渠道等。每个字段能定位到原始文本；读不清、矛盾、缺失时标记“待确认”。

**A3 四类行动卡（P0）**：保留“用药安排／复查安排／康复禁忌／就医提示”。每类卡按需出现，不强制患者四类都填满；高血压案例的“血压监测计划”可以存为医嘱相关的“其他安排”，同时链接到 B 的血压记录模板，避免机械地把它塞进药卡。

**A4 逐条核对（P0）**：草稿卡显示两列“原始医嘱／整理后的字段”。动作是“改内容／这项待确认／确认这条”；核对的是文字是否忠实，不等于患者完成治疗。家属代操作显示“家属周雯录入；核对者：周雯”，绝不能冒称“患者本人已核对”。

**A5 提醒与记录（P0 做前台能力，P1 真实提醒）**：只有用户核对过、有确定日期且主动开启的安排才设提醒。用药类允许记录“我记下本次已服用”，复查类允许记录“资料已准备／本人标记已完成”，但均不推断实际依从性。无真实后台提醒时清楚写“模拟提醒”，不可声称可靠推送。

**A6 待确认转待问（P0）**：例如“医嘱只写骨科门诊，需不需要重新挂号不清楚”；点击“一键记到待问”，写入一个带 `instructionId` 的 Question。后续在 B 和 C 自动出现，不再要求患者重复填写。

**A7 就医提示与渠道（P0 静态）**：仅展示现有医嘱明确交代的提示，保持原话，不与患者记录做症状匹配；如渠道实际未核实，则不展示可拨打的虚构电话。页面固定说明：“本工具不是实时医疗或急救服务；突发严重不适请通过当地适用的急救渠道及时求助。”

### 4.3 模块 A 的“下一件事”逻辑

从本周期 `verified` 且日期明确、未归档的安排中选择最近的可执行事项；来源不明、需进一步确认的日期不进入倒计时。不根据患者测量值或症状自动新建行动任务。不为无任务的日子制造签到；可以显示“目前没有新的已确认安排”。

### 4.4 模块 A 的典型异常

- 医嘱图片模糊：保留原图/原文和未识别字段 → 用户手填，不补造文字。
- “术后14天”但缺失手术日期：不按出院日期推断；显示“需核对手术日期与复查日”，不设提醒。
- 用户点击“已核对”后修改药名：修改项恢复待核对，相关提醒失效或暂停待重新确认。
- 模拟联系电话只有 `0577-XXXX-XXXX`：不可拨号，清楚标“示例号码”。

### 4.5 验收标准

A-AC1 从合成说明录入 ≥3 类卡且每张可见原始来源；A-AC2 日期信息缺失不被补齐；A-AC3 新增执行记录在 S01 和 C 同步；A-AC4 A 创建的待问问题在 B/C 实际可见；A-AC5 核对状态与执行状态明确分离。

## 5. 模块 B：诊后记录与疑问（记录）

### 5.1 重新统一定位

本模块不定位为开放式“AI 医疗问答”。它做三件事：**留住发生过的事情、把不理解的地方说明白、帮助找到已有可信资料或合适的现实沟通渠道**。如果是需要个人医学判断的问题，系统不答，只提供整理问题与渠道。

### 5.2 一条记录的输入流程

首页或记录页点“记一件事” → 文字输入／语音录入（P1）→ 保存原话与时间 → 用户选择去向：

- “仅记录变化”：作为 Observation 入时间线，复诊前可选择是否展示；
- “加入待问”：既保留 Observation，也创建关联 Question；
- “仅自己保存”：隐私 `private`，不进入对外摘要候选的默认选中项；
- “查看联系渠道”：跳转已核实渠道，**点击不代表已联系或医生已收到**。

为避免误操作，建议先完成保存，再提示去向；不必在保存之前回答大量问题。

### 5.3 三种输入形态与输出

| 输入 | 对应 UI | 保存为 | 复诊汇总方式 |
|---|---|---|---|
| 自由文字“昨晚睡不踏实，伤口跳着疼” | 文本框／语音转文字核对 | 原话、发生时间、记录者 | 可引用原话或用户核对过的改写 |
| 数值“11月9日早上血压 132/78 mmHg” | 自选血压模板 | 具体数值、单位、时间 | 按日期列出，不判断控制效果 |
| 自选疼痛评分“5/10” | 疼痛 0–10 数值模板 | 主观评分、时间、部位（可选） | 如实列出记录次数/评分，不自动解释严重程度 |

体重模板同理；监测项目是**工具**，不强制每天填写。原文中已有的监测频次可以显示在医嘱安排里，但软件不自行增加监测要求。

### 5.4 疑问处理机制：安全优先而非开放诊断

| 用户问题类型 | 系统允许的答复 | 禁止的答复 |
|---|---|---|
| “医生写的复查时间和地点是什么？” | 引用当前医嘱原文；缺失则说“资料未写明” | 编造科室/时间/预约成功状态 |
| “复诊需要带哪些材料？” | 如原医嘱写明则逐字列出；不确定转待问 | 补充并非原文的医学检查要求 |
| “这个名词是什么意思？” | 可选提供来源明确的通俗术语说明，标注一般性信息且不针对个人 | 以术语解释推导诊断、药物调整 |
| “头晕是不是药的问题？是否需要停药？” | 保存原话，整理成“想向医生确认”的问题，展示已核实联系渠道 | 判断药物是否导致症状、建议停药或继续用药 |
| “伤口痛算不算感染？我该做什么？” | 不评价是否感染；引导记录事实，展示既有医嘱就医提示及求助渠道 | 个人化风险评级、保证安全、延迟就医的建议 |

**分类失败降级**：不确定该问题是否触及个人医学判断时，统一走“记录／待问／现实渠道”路径。系统不做自动病情分级，亦不从聊天文本触发“你可能有某疾病”的结论。

### 5.5 AI 改写的输入/输出合同

输入仅限：当前选定 `Observation` 原文、用户明确提供的时间与“将它整理成待问问题”的意图；输出只允许重述事实、保留不确定性、提出要向医生确认的问题。不得添加患者未提供的频率、严重程度、病因或检查结论。页面显示原话与改写并列，用户可“采用／编辑／保留原话”。API 失败则保留原话，绝不显示伪造的回答。

例：原话“昨晚伤口跳着疼，睡不踏实。” → 草稿“昨晚曾有伤口跳痛并影响睡眠，想向医生确认如何处理。”。这是**语言整理**，不是诊断。

### 5.6 出院前“该问医生什么”（P1）

固定三四条通用问题模板，来自现有疑问清单的合理转换，如“下一次复查具体时间和地点是什么？”“有哪些已交代的活动限制需要确认？”“遇到问题应联系哪个既有渠道？”“这次是否需要带上检查资料？”。模板只**提供问句**不提供医疗答案，用户决定是否放进待问清单。

### 5.7 验收标准

B-AC1 任何新增原话可以在记录列表找到；B-AC2 AI 改写能回到原话查看；B-AC3 私密记录默认不外发；B-AC4 选择待问以后 C 自动出现；B-AC5 数值及发生时间可进入复诊卡且不产生趋势判断；B-AC6 不会回答个人化诊断及药物调整问题。

## 6. 模块 C：复诊沟通桥（复诊）

### 6.1 为什么保留三段式

复诊卡不是再次“总结一切”，而是为医生/患者沟通准备一个有来源的提纲。沿用现有纸感设计的三段结构，可减少现场找信息的负担：

I. **已有安排与处理记录**（只报事实）；II. **期间本人或家属记录的变化**（原话与结构化数据）；III. **想问医生的问题**（方便逐条沟通）。

### 6.2 复诊前生成步骤（P0）

1. 用户进入“复诊”，显示当前周期和资料概览：已核对安排数、变化记录数、待问数。
2. “选择本次展示的内容”：行动记录可选、变化记录可选、待问问题可选；`private` 初始全不选，并有明显标识。
3. 系统使用**程序汇总优先**：如“11月6、8、11日记录了3次”，计数按真实日志计算；没有记录的日子写“未记录”。
4. 可用 AI 对用户选中的自由文字做受限整理，但每行必须保留 `sourceIds`；避免“恢复良好／病情稳定／坚持每日记录”等无依据的结论。
5. “逐条核对”页：每行旁有“查看原话/来源”“修改”“不放进这次复诊卡”；完成明确核对后产生展示版。
6. 展示版显示核对人、核对时间和“患者／家属自述，非医学审核”。
7. 若选择内容或来源改变，原先的已核对状态失效，需再核对；打印或分享只能取最新用户核对的版本。

### 6.3 建议的复诊卡展示结构

```text
复诊沟通卡　患者自述 · 非医学审核
本轮：11月5日出院—待核实复诊日　核对者：周建国／周雯（真实操作时按实际标注）
──────────────────────────────
一、原有安排及执行记录
- 骨科复查：日期正在核对；需携带出院小结（来源：出院小结原文）
- 用药安排：见已核对的原医嘱；系统有 N 条本人记录的服用行为
- 未记录的日期不视为未服药
二、期间记录的变化
- 11月16日：‘昨晚伤口跳着疼，睡不踏实’（周建国原话）
- 疼痛评分：有 N 条日期明确的记录（仅展示本人选择的数据）
三、此次想问的问题
□ 下一次复诊要不要重新挂号？
□ 最近伤口疼痛如何向医生进一步说明？
──────────────────────────────
[查看来源]　[诊室模式]　[本轮归档]
```

这里的 `N` 是 UI 示例占位，实际软件必须显示基于真实合成日志的数值；不能把占位作为完整演示内容。**特别注意**：若家属而非患者核对，标明“家属核对”，不可写“患者本人核对”。

### 6.4 诊室模式（P1，优先做）

同一份摘要切换为更大字（建议可选 22–26px）、清楚的分区、一次一条待问内容；允许用户逐条标记“已问过”，不显示“已答复”“医生已同意”。离开诊室模式不会丢失标记。可保留大字版打印/分享入口，但没有真正实现的导出能力不得在视频中宣称已实现。

### 6.5 归档与下一周期（P0）

用户主动点“结束本轮”；确认弹层准确说明“本轮软件提醒将停止；不表示治疗结束，不影响医院预约”。完成后旧周期只读。再次就诊得到新的医嘱时，从新材料建立新周期；之前药物、提醒、禁忌**不自动继承**。可在历史页查看旧周期的摘要，但不把它当成下一轮的有效安排。

### 6.6 验收标准

C-AC1 A/B 的真实记录自动成为候选；C-AC2 每段摘要可追溯来源；C-AC3 修正后需重新核对；C-AC4 私人记录默认排除；C-AC5 “已问过”与“已回答”区分；C-AC6 归档后本轮提醒实际失效；C-AC7 无记录、未知与事实记录不被 AI 夸大。

## 7. 适老化与家庭照护设计：从失误模式出发

### 7.1 不只改字体，而是减少四类任务失败

| 可能失败模式 | 设计响应 | 证据等级 | 优先级 |
|---|---|---|---|
| 打字慢、术后单手操作 | “记一件事”支持语音原始录制；可选转写但需本人核对 | 当前人物假设＋通用可及性原则，待实测 | P1 |
| 日期语义混淆（术后 vs 出院后） | 日期依据卡：参照事件、原文、计算依据、待核对；无法确定则不提醒 | 骨科案例已出现确切的设计错误 | P0 |
| 家属代操作后身份不清 | 新记录显式“由谁录入／谁核对”，不自动冒称患者本人 | 情境推断，待患者访谈 | P1 |
| 临诊前想问什么记不住 | 诊室模式大字逐条问题；勾选“已问过” | 现有问题清单支持“要问什么”，记忆困难仍待验证 | P1 |
| 阅读小字困难 | 主体 18–20px，缩放支持到更大，关键按钮 ≥48px；图标旁始终有文字 | 工信部适老化规范、WCAG；具体数值为项目选型 | P0 |
| 看不懂专业词或怕把内容认错 | 患者原话／原始医嘱／AI 整理三种来源清楚区分，逐条核对可撤销 | 数据正确性需求＋设计原则 | P0 |
| 切换 App 找电话困难 | 已核实渠道一键拨号；合成假号码不得拨号 | 通用原则，待用户测试 | P1/P2 |
| 一直不知道当前在哪里 | 三导航结构，显示“这是本轮安排”，保存后明确反馈，支持返回／撤销 | 可访问性与认知负担设计原则 | P0 |

### 7.2 视觉与交互标准（沿用纸感风格，不另换 UI）

- 保留暖纸白背景、深青关键按钮、原话白底引用、AI 浅青底、私人记录杏色；只用颜色还不够，所有状态必须配文字。
- 普通正文建议至少 18px 左右的移动端呈现，配合动态字号；章节标题大于正文；卡片不依赖字体缩小容纳过长医嘱，允许扩展查看。
- 关键按钮触控高度建议 48–56px，按钮间有足够间隔；不依赖长按、拖拽、隐藏滑动才能发现重要功能。
- 正文行距 ≥1.4 作为团队设计目标；在 200% 文字缩放下不截断药名、日期、确认状态和按钮文案。
- 动画只确认保存、核对、展示来源关系；尊重系统减少动态效果设置。不要通过红色闪烁、倒计时吓唬用户。
- “识别到的医嘱”不要显示为经过医学确认。应写“AI 整理草稿，尚待您核对”，必要时突出“请按医生原文确认”。
- 录音必须在麦克风权限同意后进行；失败可退回文字输入。若只有录音但未接入转写，UI 必须称“已保存语音”，不能显示编造的文字稿。

### 7.3 我最推荐的三项比赛演示特色

**第一项：来源核对＋日期澄清**。把“术后14天”和“出院后14天”当作不同时间参照；发现缺少参照日期时保留待确认。它不仅适老，也能体现医疗信息可靠性。

**第二项：家属协助但不混淆身份**。女儿帮忙录入出院小结，页面显示“周雯代录／周雯核对”，患者本人后来可以重新查看；该交互用最小成本体现家庭照护场景。

**第三项：诊室模式**。患者真正拿着卡去见医生，不需要现场学习复杂操作；字号放大、疑问逐条勾选，将“整理信息”推进到“支持实际沟通”。

语音记录也值得演示，但如果四天内浏览器录音、权限、存储不稳定，优先保证核心数据闭环；演示不能假装语音真的已经保存。

## 8. 双场景流程演示脚本

### 8.1 主演示：62岁骨科术后患者与女儿（建议视频主体 3–4 分钟）

**前提**：全部是合成数据。保留现有人物“周建国、周雯”作为虚构用户；合成医嘱需医学队友审核。**时间错误修正**：原始案例设11月5日为术后第3天出院，却从11月5日计算“术后14天＝11月19日”，是不正确的。演示版建议改为“医嘱直接注明具体复查日11月19日”（经医学审阅作为合成资料），同时把“术后14天”另设为缺失手术日期的待确认示例；**不要擅自把患者真实术后安排改为其他日期**。

| 步骤／镜头 | 用户操作与 UI 反馈 | 底层写入及验收点 | 讲解词建议 |
|---|---|---|---|
| 01 建立本轮 | 女儿选“术后出院”，建周期；上次出院11/5，下次复查日期待核对 | 新建 `Cycle`，`reviewAt` 可空 | “只管理出院到复诊之间的一段时间。” |
| 02 医嘱导入 | 粘贴经审阅的合成出院材料；生成用药／复查／康复／就医提示卡 | 建 `SourceDoc`、`Instruction(draft)`，每卡可查看来源 | “AI 负责整理，不负责重新开医嘱。” |
| 03 故意展示日期缺口 | 术后14天但无手术日，显示“缺少计算依据”；患者先保存待确认 | `verifyStatus=pending`；不设无来源提醒；一键建 Question | “遇到不知道的信息，系统不帮医生猜。” |
| 04 逐项核对 | 已明确的卡由女儿核对，显示“周雯代录／周雯核对”；进入首页显示下一件事 | 核对人与已记录执行分开；无需全部卡满 | “代记有记录，核对不等于已完成。” |
| 05 记录执行 | 模拟患者对某项操作点“我已记录执行”；出现时间与记录者 | 新增 `ActionLog`，C 可选择 | “记录做过什么，不替用户判定疗效。” |
| 06 语音/文字记事 | 周建国说／输入“昨晚伤口跳着疼，没睡好”；保存原话，选择“加入待问” | 新增 Observation + Question；原话与来源保留 | “只需说一句，问题便不会丢。” |
| 07 AI 整理 | 点击“帮我整理成问题”，显示原话／草稿对照并采用 | 只修改表达，不回答病情 | “AI 不判断正不正常，只帮患者表达清楚。” |
| 08 家属私密记录 | 周雯录一条家属观察，选择“仅自己保存” | `privacy=private`，生成摘要默认不选 | “家属信息有来源，私人内容不自动外发。” |
| 09 复诊准备 | 选择已核对安排、执行日志、患者变化及待问；摘要三段自动生成 | 每行含 `sourceIds`；结构化次数来自真实日志 | “两周信息汇成一页，且每句都能追溯。” |
| 10 摘要纠错 | 展示故意注入的错误“每日记录”“恢复良好”，通过原始来源发现并删除／修正 | 编辑后重新核对，原核对标识失效 | “我们更重视可核对，而不是让 AI 看起来永远正确。” |
| 11 诊室模式 | 大字查看复诊卡，逐项勾“已问过” | 问题 status=asked，非医生已回复 | “现场只需一眼看到变化与待问事项。” |
| 12 归档 | 点“结束本轮”，确认提醒停止；历史只读，可新建周期 | Cycle=archived；本轮提醒关闭 | “一次复诊结束后，旧医嘱不会自动带入下一轮。” |

**一段完整患者视角台词**：“女儿帮我把出院材料放进去，我一项项核对；回家后有不舒服就记下来；快到复诊时，不用再拼命回想两周内发生过什么，拿出这张卡告诉医生就行。”注意这是模拟台词，不应冒充真实患者评价。

### 8.2 扩展验证：高血压患者（约 25–35 秒）

用户切换到陈淑兰的**独立合成周期**（不是把骨科周期改名）。导入既有门诊说明：系统沿用相同 `Instruction`，主要显示用药、监测相关安排和复诊事项；由 B 记录4个日期的血压数值与“吃完药有点晕乎”的原话；把“不知道要不要重新挂号”转为待问。C 仍生成相同三段式沟通卡，只是第二段换为“血压记录的日期与数值／患者头晕自述”，不能得出“血压控制良好”。

**演示结论**：同一份数据结构和三模块流程可完成第二种场景，不需要重新开发专属慢病系统；这验证的是**软件机制可复用**，而非已获得真实慢病患者的需求或临床效果验证。

### 8.3 面向评委的 30 秒价值讲述

“很多诊后工具只做提醒或聊天。我们把医生已交代的安排、患者在家记录的变化、想问的问题，放在同一个复诊周期里。AI 提取和整理信息，但不能自创医嘱；所有摘要都能找回原文，由患者核对。我们先用术后场景做完整闭环，再用高血压复诊展示流程可复用，还把家属代记和诊室大字模式融入了实际任务。”

## 9. 开发合同：给 WorkBuddy 的实现说明

### 9.1 推荐实现次序

1. 先定义上述 7–8 个对象及状态关系，确保所有页面由共享状态渲染；开发过程需截图保留为比赛里程碑。
2. 用人工粘贴的合成医嘱先做 A；OCR 和 AI 提取作为可替代增强，不允许阻断主流程。
3. B 的自由记录和待问先真实保存、跨页同步，再做可选 AI 改写；语音依赖浏览器能力，可失败降级。
4. C 先做程序模板汇总和来源点击，再做 AI 语言润色、核对版本、诊室模式与归档。
5. 所有演示数据可一键重置；骨科与高血压预设 **独立 cycleId**，无数据串线。

### 9.2 对 AI 调用的四条硬约束

**提取**：只从可见输入中抽取，不知道的字段明确留空，并保留来源片段。**改写**：只整理选中的患者原话，保留“不确定”等语义。**摘要**：只读取用户勾选过的 `sourceIds`，只写事实，不得创造疗效评价。**失败**：服务调用报错、没有证据、输出格式错误时，回退原文／程序汇总，不伪造数据。

### 9.3 提醒与后端的诚实边界

如实现的是网页内模拟通知，必须持续展示“模拟提醒”；浏览器关闭后无法保证到达时，就不得写“后台可靠提醒已实现”。若采用本地存储，必须告知“换设备不自动同步”。一键拨打仅用于已核实真号码；不得给合成号码绑定拨号动作。

## 10. 优先级、职责和四天里程碑

| 级别 | 必须交付 / 可能增值 | 失败后的处理 |
|---|---|---|
| P0（先完成） | 一个真实运行的骨科数据闭环、四类卡、来源核对、待问同步、手动记录、三段复诊卡、版本核对、私人记录保护、归档、双周期互不串线 | 不可删；优先缩减其他功能 |
| P1（有价值） | 语音真实录制、家属代记、日期依据、诊室模式、高血压复用演示 | 若时间紧保留最稳的两项特色 |
| P2（可推迟） | OCR 批量导入、朗读、一键拨号、多账号家庭协作、PDF 专业导出、完整可溯源科普知识库、可靠后台提醒 | 如未做不应出现在“已实现”清单 |

**第1天**：固定对象与状态；骨科医嘱手动录入→四类卡→A/B 写入。**第2天**：A/B 数据真正进 C；来源核对、修改失效、归档与保护。**第3天**：挑两项适老化特色＋高血压独立周期测试；请医学生审核合成医嘱和语言。**第4天**：异常用例、演示录制、作品说明／里程碑截图／主体代码和运行说明打包；比赛主体开发必须通过 WorkBuddy，不能把已有设计原型误写为 WorkBuddy 已完成的主体开发。

**职责**：你负责产品流程、信息结构、交互与开发验收；医学生甲负责骨科合成材料的医学措辞及临床边界核对；医学生乙负责复诊卡接收方视角、访谈与高血压案例合理性。最好请一位相关科室医生或护士看一次信息提取和复诊卡的可用性；如暂不能做到，明确记“待临床核对”。

| 编号 | 操作／输入 | 必须出现的结果 |
|---|---|---|
| T01 | 输入含多种医嘱类别的合成说明 | 卡片可逐项核对、来源可见，未写明字段不补齐 |

## 12. 需要队友和医务人员尽快确认的决策

1. **骨科合成医嘱**：药品、频次、禁忌、出院后伤口处理、预警措辞、复查时点均需审阅，不能把未审核示例展示为临床标准。
2. **日期锚点**：原案例“术后第三天出院，术后14天从出院日起算”有错误；务必改合成材料，保留该错误作为系统测试，而非正式医嘱示例。
3. **医生接收摘要的可行性**：希望医生30秒看到什么？医学生先提出草案，最好由骨科或随访护士核对顺序与长度。
4. **家庭照护**：患者是否会自己看手机？家属代录是否常见？是否需要标注“患者已查看”还是只能标注“某某已核对”？
5. **录音和隐私**：是否真的能在目标手机浏览器稳定录音，是否仅本机保存，是否会未经同意将内容上传到第三方 AI 服务？
6. **安全出口**：真实渠道未核实时，只能显示中性的联系方法说明，不能声称已连接到医院；严重或突发不适提示应清楚指向现实紧急求助，不进行自动病情诊断。
